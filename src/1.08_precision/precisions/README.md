# 数据精度：从 fp32 到 fp8

训练里的每一个数都要用某种格式存在显存里。格式越短：

- 每个数占的字节越少，**显存省了，搬运也快了**；
- GPU 对短格式的矩阵乘法算得更快；
- 但能表示的数越粗、范围越窄，**结果越不准**。

这一节的问题是：**每一类数各需要多少位？哪些可以省，哪些不能省？**

---

## 0. 地图：训练里有哪些数，论文是怎么选的

### 0.1 训练里有哪些数

| 类别 | 是什么 |
|---|---|
| **参数** | 模型的权重，比如 `attn_wq`、`lm_head` |
| **梯度** | 每个参数一个，反向传播算出来，告诉我们参数该往哪改 |
| **优化器状态** | Adam 给每个参数额外记的两个数：m（梯度的平均）和 v（梯度平方的平均） |
| **激活** | 前向计算的中间结果，比如每一层的输出、注意力矩阵。很多要存下来，反向传播时再用 |

计算也分两类：

- **矩阵乘法**：计算量几乎都在这里。
- **其他运算**：softmax 里的 exp 和求和、rmsnorm 里的平方和开方、relu、残差相加。计算量很小，但有些对精度很敏感。

### 0.2 论文的路线

降低精度的历史，可以看成一条主线：**参数始终留一份 fp32；矩阵乘法的输入越来越短；对精度敏感的地方始终保留高精度。**

| 方案 | 参数 | 梯度 | 优化器状态 | 矩阵乘法 | 其他运算 | 激活 |
|---|---|---|---|---|---|---|
| fp32 | fp32 | fp32 | fp32 | fp32 | fp32 | fp32 |
| **fp16 混合精度**<br>Micikevicius et al. 2018 | fp32 主副本 + fp16 副本 | fp16，更新到 fp32 主副本上 | fp32 | fp16 输入、fp32 累加 | 求和、softmax 用 fp32 | fp16 |
| + loss scaling | | | | | | |
| **bf16 混合精度**<br>Gopher、BLOOM、Llama 3 等 | fp32 主副本 + bf16 副本 | bf16，更新到 fp32 主副本上 | fp32 | bf16 输入、fp32 累加 | softmax、loss 用 fp32 | bf16 |
| 不需要 loss scaling | | | | | | |
| **fp8**<br>DeepSeek-V3 | fp32 主副本 | 权重梯度 fp32 | **bf16** | 线性层用 **fp8**（分块缩放）；embedding、输出层、注意力保持 bf16 | 保持高精度 | 存给反向的部分用 fp8 |

表里的"主副本""累加""loss scaling""分块缩放"后面各节会一一解释。

### 0.3 我们的实验

这个目录下每种精度一个文件。它们分成三组：

| 组 | 文件 | 对应 |
|---|---|---|
| **基线** | `fp64`、`fp32`、`tf32` | 所有数都用同一种格式，只是位数不同。tf32 是硬件上的一个开关，见第 6 节 |
| **论文路线** | `fp16_scaler` → `bf16_autocast` → `fp8` | fp16 混合精度 → bf16 混合精度 → fp8（简化版） |
| **消融** | `bf16_pure`、`fp16_noscaler` | 从论文的方案里**去掉一个关键部件**，看它是不是真的必要（"消融"就是这个意思）。前者去掉 fp32 主副本，后者去掉 loss scaling |

每个文件规定同样几件事：

```python
dtype = torch.float32     # 参数和优化器状态用什么格式存
autocast = torch.bfloat16 # 矩阵乘法用什么格式算，None 表示不换（autocast 见第 3 节）
tf32 = False              # fp32 的矩阵乘法是否用 tf32 算（见第 6 节）
loss_scale = None         # loss 放大的初始倍数，None 表示不放大（见第 4 节）
linear = None             # 层内线性层的特殊实现，fp8 时换成 fp8 矩阵乘法（见第 7 节）
```

## 1. 浮点数怎么表示

一个浮点数由三部分组成，就像科学计数法 $6.02 \times 10^{23}$：

$$x = (-1)^{\text{符号}} \times 2^{\text{指数}} \times 1.\text{尾数}$$

- **指数位**决定能表示多大、多小的数，也就是**范围**；
- **尾数位**决定有效数字有几位，也就是**精度**。

总位数固定，给指数多一位，尾数就少一位：

| 格式 | 总位数 | 指数 / 尾数 | 最大值 | 最小的正规数 | 相对精度 |
|---|---|---|---|---|---|
| fp64 | 64 | 11 / 52 | $1.8\times10^{308}$ | $2.2\times10^{-308}$ | $2.2\times10^{-16}$（约 16 位十进制） |
| fp32 | 32 | 8 / 23 | $3.4\times10^{38}$ | $1.2\times10^{-38}$ | $1.2\times10^{-7}$（约 7 位） |
| tf32 | 19 | 8 / 10 | 同 fp32 | 同 fp32 | $9.8\times10^{-4}$（约 3 位） |
| fp16 | 16 | 5 / 10 | 65504 | $6.1\times10^{-5}$ | $9.8\times10^{-4}$（约 3 位） |
| bf16 | 16 | 8 / 7 | 同 fp32 | 同 fp32 | $7.8\times10^{-3}$（约 2 位） |
| fp8 E4M3 | 8 | 4 / 3 | 448 | $1.6\times10^{-2}$ | 0.125 |
| fp8 E5M2 | 8 | 5 / 2 | 57344 | $6.1\times10^{-5}$ | 0.25 |

几个名词：

- **相对精度**：在 1 附近，相邻两个能表示的数差多少。bf16 里，1 的下一个数是 1.0078，中间的数都表示不了，只能就近取一个，这叫**舍入**。
- **溢出**：数太大，超过了最大值，变成 inf（无穷大）。
- **正规数和非正规数**：比"最小的正规数"还小的数，格式会牺牲有效位数，勉强再表示一段，这一段叫非正规数。fp16 的非正规数最小到 $6\times10^{-8}$。
- **下溢**：数比非正规数还小，直接变成 0。

**fp16 和 bf16 都是 16 位，取舍正好相反：** fp16 精度高一点，范围只到 65504；bf16 精度只有 2 位多有效数字，范围和 fp32 一样大。

## 2. 舍入：小的更新会被"吃掉"

浮点数的加法有个陷阱：**一个大数加上一个很小的数，结果可能还是那个大数。**

```python
>>> torch.tensor(1.0, dtype=torch.bfloat16) + 0.003
tensor(1., dtype=torch.bfloat16)
```

0.003 比 1 附近间距（0.0078）的一半还小，加上去以后又被舍入回 1。

这对训练是致命的。参数更新就是 `p -= lr * update`：参数本身在 0.1 左右，每一步的更新却可能只有 $10^{-4}$ 甚至更小。粗略算一下：

- 参数在 0.1 附近时，bf16 相邻两个数之间差约 0.0005；
- Adam 每步的更新大约是 学习率 × $|m/\sqrt{v}|$，后一项常常只有 0.1 左右；
- 所以学习率降到 0.005 以下，很多更新就小于间距的一半，加不上去了。

学习率线性衰减时，后一半的训练都在这个区间。

**解决办法：**

- **fp32 主副本**：参数另外存一份 fp32 的，叫"主副本"（master weights）。每一步的更新都加在主副本上，fp32 足够精细，小的更新不会丢；算前向时，再从主副本转出一份低精度的副本来用。这是混合精度的做法。
- **随机舍入**（stochastic rounding）：不总是就近舍入，而是按距离远近的比例，随机向上或向下取。单看一次可能舍错，但平均下来，小的更新也能加上去。
- **Kahan 求和**：单独记下每次被舍掉的那一点，下次再补回去。

Zamirai et al. (2020) 发现，后两种方法能让纯 bf16 训练追平 fp32。Gopher（Rae et al. 2021）在附录里比较过：bf16 参数加随机舍入，仍然不如保留一份 fp32 主副本；有了主副本，就和全程 fp32 训练没有区别。

## 3. 混合精度：只把矩阵乘法换成 16 位

**混合精度**（mixed precision）的意思是：不同的数、不同的运算用不同的精度，而不是全部统一。Micikevicius et al. (2018) 提出的做法有三条：

1. **参数存 fp32 主副本**，优化器也在 fp32 上更新。避免第 2 节的问题。
2. **矩阵乘法用 16 位输入，但用 fp32 累加。** 矩阵乘法的每个输出，都是几十到几千个乘积**加起来**的结果，这个"一路加起来"的过程叫**累加**。乘积有一点误差没关系，误差会互相抵消；但累加的结果如果也只用 16 位存，就会像第 2 节那样，后面加上去的小数被吃掉。所以累加要用 fp32。
3. **fp16 时还要放大 loss**，见第 4 节。

为什么只换矩阵乘法：GPU 上有专门做矩阵乘法的硬件单元，叫 **Tensor Core**，它对 16 位输入的吞吐是 fp32 的好几倍，而且内部本来就用 fp32 累加。计算量又几乎都在矩阵乘法里，所以只换这里，就拿到了大部分的加速。

### autocast：PyTorch 的自动转换

自己动手给每个运算决定精度太麻烦。PyTorch 提供了 **`torch.autocast`**：在它的 `with` 代码块里，PyTorch 会按一张内置的表，**自动给每个运算选精度**。

```python
with torch.autocast('cuda', dtype=torch.bfloat16):
    probs = softmax(gpt(x))
```

- **矩阵乘法**：自动把输入（包括 fp32 的参数）临时转成 bf16 再算。
- **exp、log、pow、sum 这类对精度敏感的运算**：自动转成 fp32 再算。
- **relu、加减法这类运算**：输入是什么格式就用什么格式。

参数本身不变，还是 fp32，转出来的 bf16 副本只在这一次计算中使用。这正好实现了上面第 1、2 条：参数是 fp32 主副本，矩阵乘法用 bf16。

我们实测过：手写的 softmax 和 rmsnorm 里，`exp`、`pow`、`sum` 的输出都是 fp32，只有 `logits - max` 这一步是 bf16。

**我们的实验里**，bf16 混合精度和 fp32 完全打平。

**显存省得不多**，只比 fp32 少约 7%。参数、梯度、Adam 状态都还是 fp32，还要多存一份 bf16 副本，省下来的只有一部分激活。

## 4. fp16 和 loss scaling

fp16 的问题是**范围太小**，小于 $6\times10^{-8}$ 的数会下溢成 0。而梯度往往很小，比如对 4096 个 token 的 loss 取平均以后，每个位置的梯度都被除了 4096。

### loss scaling：先放大，再缩回去

**loss scaling** 的思路很简单：

1. 反向传播之前，先把 loss 乘一个大数 $S$，比如 65536（$2^{16}$）；
2. 反向传播是一连串乘法，所以**所有梯度都跟着放大了 $S$ 倍**，原本会下溢成 0 的小梯度，现在能表示了；
3. 更新参数之前，再把梯度除以 $S$，变回原来的大小。这一步在 fp32 里做，不会下溢。

比如一个梯度是 $10^{-9}$，fp16 里会变成 0；放大 65536 倍后是 $6.6\times10^{-5}$，fp16 能存下；最后再除回去。

### 动态调整倍数

$S$ 也不能太大，否则大的梯度会**溢出**成 inf。合适的 $S$ 又会随训练变化，所以通常**动态调整**：

- 发现梯度里有 inf：说明放大过头了，**这一步不更新**，$S$ 减半；
- 连续 2000 步都没有溢出：说明还有余量，$S$ 翻倍。

PyTorch 里有个现成的工具专门做这件事，叫 **`GradScaler`**（文件名里的 **scaler** 就是指它）。`train.py` 里是这样用的：

```python
scaler = torch.amp.GradScaler('cuda', init_scale=2.0 ** 16, growth_interval=2000)
...
scaler.scale(loss).backward() # 1. 把 loss 乘以当前的倍数，再反向传播
scaler.step(optimizer)        # 2. 把梯度除以倍数，缩回原来的大小；如果梯度里有 inf，这一步就不更新
scaler.update()               # 3. 调整倍数：这一步溢出了就减半，连续 2000 步没溢出就翻倍
```

它做的事情就是上面说的三步。不需要 loss scaling 的精度，创建时传 `enabled=False`，这三行就什么都不做，`scaler.scale(loss)` 原样返回 loss。

**我们的实验里：**
- 不放大时，矩阵参数的梯度里有约 12% 下溢成了 0；放大以后只剩 0.03%。
- 倍数从 65536 涨到 262144，一次都没有溢出。
- 但**不放大也没有出问题**，结果和放大的一样。我们的模型小，被下溢掉的只是本来就很小的那部分梯度。

**在大模型中：** fp16 时期的大模型（如 Megatron-LM、OPT）都靠 loss scaling 训练，但训练不稳定是常态。BLOOM 的报告提到，他们早先在 V100 上用 fp16 训练 104B 模型时，遇到了无法恢复的发散；最终改用 bf16 混合精度，解决了这个问题。

## 5. bf16：为什么成为主流

bf16（brain floating point）是 Google Brain 为 TPU 设计的格式：**直接把 fp32 的尾数砍掉 16 位**，指数位保持 8 位不变。

- **范围和 fp32 一样**，梯度不会下溢，**不需要 loss scaling**。
- **和 fp32 互相转换极其简单**：截掉或补上低 16 位就行。
- 精度很粗，但混合精度里只有矩阵乘法的输入用它，累加和参数都在 fp32，影响不大。

Kalamkar et al. (2019) 系统地验证了 bf16 混合精度在各类模型上都能追平 fp32。从 A100 开始，NVIDIA GPU 也原生支持 bf16。之后的大模型几乎都用 bf16 混合精度，比如 Gopher、BLOOM、Llama 3。

---

## 6. tf32：一个硬件开关

tf32 不是一种存储格式，而是 NVIDIA 从 A100 开始提供的**矩阵乘法计算模式**：输入、输出都还是 fp32，只是在 Tensor Core 内部把尾数截到 10 位来算。

```python
torch.backends.cuda.matmul.allow_tf32 = True
```

一行设置，模型代码完全不用改。我们实测，大矩阵上 tf32 比 fp32 快约 2 倍，训练结果和 fp32 打平。PyTorch 从 1.12 起默认关闭了它，需要手动打开。

## 7. fp8：再砍一半

### 7.1 两种格式

8 位实在太少，所以 fp8 有两种分法（Micikevicius et al. 2022），名字里的 E 和 M 分别是指数位和尾数位的位数：

- **E4M3**：4 位指数、3 位尾数，最大 448，精度高一些。通常用于前向。
- **E5M2**：5 位指数、2 位尾数，最大 57344，范围大一些。通常用于反向的梯度，因为梯度的大小变化更大。

### 7.2 缩放和量化

把数转成更粗的格式，叫**量化**。fp8 的范围太窄，不能直接转：大于 448 的会溢出，太小的会下溢。所以先给整个张量乘一个**缩放因子**，把它缩放到 fp8 刚好能装下的范围，再转格式；用的时候，再除回去。

```python
def quantize(x, fmt):
    # 缩放因子 = 张量里绝对值最大的数 / 格式能表示的最大值，这样最大的数正好落在格式的上限
    scale = x.abs().max().float().clamp(min=1e-12) / torch.finfo(fmt).max
    return (x / scale).to(fmt), scale
```

GPU 的 fp8 矩阵乘法 `torch._scaled_mm` 会顺便把两个缩放因子乘回去：

```python
torch._scaled_mm(qa, qb, scale_a=sa, scale_b=sb, out_dtype=torch.bfloat16)
```

一个线性层有三次矩阵乘法：前向 $y = xW^\top$，反向对输入求梯度 $\partial x = \partial y\, W$，对权重求梯度 $\partial W = \partial y^\top x$。我们的 `fp8.py` 三次都用 fp8。

### 7.3 逐张量缩放的问题：离群值

我们是**整个张量共用一个缩放因子**（逐张量缩放）。问题出在**离群值**，也就是比其他数大得多的少数几个数：

- 缩放因子由最大的那个数决定；
- 如果有一个数是其他数的 100 倍，为了装下它，其他所有数都被压到很小，挤在 fp8 能表示的最小的那几档里，精度损失很大。

大模型的激活里常常有这样的离群值。

### 7.4 DeepSeek-V3 的做法

DeepSeek-V3 是第一个公开验证 fp8 训练能用在超大模型上的（671B 参数，14.8T token），和 bf16 基线相比，loss 的相对误差始终小于 0.25%。

- **哪些用 fp8**：线性层的三次矩阵乘法。存给反向用的激活也用 fp8，省显存。
- **哪些保持高精度**：embedding、输出层、MoE 的路由（MoE 模型里决定每个 token 交给哪几个子网络处理的那部分）、norm、注意力；参数主副本和权重梯度用 fp32；Adam 的 m 和 v 用 bf16。
- **分块缩放**：不再整个张量一个缩放因子，而是激活每 1×128 个数一个，权重每 128×128 块一个。这样一个离群值只影响它所在的那一小块。
- **全部用 E4M3**：有了分块缩放，范围不再是问题，所以梯度也用精度更高的 E4M3。
- **提高累加精度**：H800 的 fp8 Tensor Core 累加时只保留约 14 位，所以每累加 128 个数，就把部分和转到 GPU 的通用计算单元（CUDA Core）上，用 fp32 继续加。

**我们的 fp8 是简化版**，和 DeepSeek-V3 有三处不同：

| | DeepSeek-V3 | 我们 |
|---|---|---|
| 缩放 | 分块 | 逐张量 |
| 梯度的格式 | E4M3 | E5M2 |
| Adam 状态、激活 | 降到 bf16 / fp8 | 没有降 |

### 7.5 我们的实验

- **训练损失 0.008，推理时再损失 0.006。** 而且这个差距从训练一开始就有 0.01 以上，和学习率大小无关，说明是前向计算本身不准，和第 2 节"小的更新被吃掉"不是一回事。
- **当前模型上反而更慢**（22 秒，fp32 是 12 秒）。每次矩阵乘法之前，都要先求最大值、缩放、转格式，每一步都是 GPU 上单独启动的一个小程序（kernel），而当前模型的时间本来就全花在启动 kernel 上。
- **加宽到 3072 也只比 bf16 混合精度快 16%**，和纯 bf16 差不多。单独测矩阵乘法时，fp8 是 bf16 的 2.4 倍，但整个训练里只有 6 个线性层用 fp8，量化的开销又不小，加速被摊薄了。

### 7.6 前沿：更细的分块，更少的位

- **Microscaling（MX）格式**（Rouhani et al. 2023）：把分块缩放写进了格式标准，每 32 个数一块，缩放因子是 2 的幂。包括 MXFP8、MXFP6、MXFP4，NVIDIA Blackwell 架构的 Tensor Core 原生支持。
- **NVFP4**：NVIDIA 的 4 位格式，每 16 个数一块，缩放因子用 E4M3。NVIDIA (2025) 用它训练了一个 12B 模型（10T token），loss 和下游任务都追平了 fp8 基线。为此还用了几个技巧：
  - 随机 Hadamard 变换：先对数据做一次特殊的旋转，把离群值的大小"摊"到一组数上；
  - 随机舍入；
  - 部分层保留高精度。

| fp16 混合 + loss scaling | fp32 | fp16 | 1.1761 | 14.0 s | 71 TFLOPS | bf16 之前的标准 |
| bf16 混合 | fp32 | bf16 | 1.1758 | 12.5 s | 71 TFLOPS | **现在的标准** |
| fp8（简化版） | fp32 | fp8 + bf16 | 1.1834（**+0.008**） | 21.6 s | 82 TFLOPS | DeepSeek-V3，需要分块缩放 |
| 消融：去掉主副本 | bf16 | bf16 | 1.1841（**+0.008**） | 11.9 s | 84 TFLOPS | 不这样做 |
| 消融：去掉 loss scaling | fp32 | fp16 | 1.1777 | 12.7 s | — | 大模型上会出问题 |

TFLOPS 是每秒做多少万亿次浮点运算，衡量算力用满了多少。

在我们的实验里：
- 混合精度没有任何损失；
- 去掉 fp32 主副本，训练后期的小更新会被吃掉；
- fp8 的前向本身就有误差；
- 速度上，模型小的时候低精度没有优势，甚至更慢；加宽到 768 以上才拉开差距。
